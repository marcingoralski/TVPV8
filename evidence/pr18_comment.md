I tested this PR (head `5df93f9`) end to end: built it on Ubuntu 24.04 with MariaDB 10.11 and drove a real OTCv8 client (7.72 dat/spr) from a script. Two blocking problems reproduce.

### 1. Fresh install: nobody can log in

`migrations/001_player_data.sql` is never run, because the migration runner only loads `data/migrations/{n}.lua`. `schema.sql` isn't updated either, so on a database built from `schema.sql` every login fails:

```
[Error - mysql_real_query] Query: SELECT `id`, `name`, ... `blessings`, `cap`, ... FROM `players` WHERE `id` = 1
Message: Unknown column 'blessings' in 'SELECT'
```

![fresh schema](https://raw.githubusercontent.com/marcingoralski/TVPV8/2930297570f4ea169247ca4ca452295fc16df36d/evidence/fig1_fresh_schema.png)

### 2. Container contents and item attributes are wiped on relog

Steps (migration applied by hand): log in, create a backpack with 3 crystal coins and a rope, set a might ring's attributes with `/attr charges, 7` and `/attr description, ...`, then log out (server: `was removed from the game`). Then log in again from a **new client process** (server: `has logged in`, so the player is reloaded from the database).

| | Before logout | After relog |
|---|---|---|
| Backpack | 3 crystal coins, rope | **empty** |
| Might ring | "7 charges left. Engraved for PR 18 test." | **"1 charge left."**, no description |

![relog item loss](https://raw.githubusercontent.com/marcingoralski/TVPV8/2930297570f4ea169247ca4ca452295fc16df36d/evidence/fig2_relog_item_loss.png)

**Cause:** the save is fine. `Item::serializeTVPFormat` writes the item ID first, so the ring blob is `7408 0000 16 0700 07 1800 "Engraved..." 0000`. The inventory loader in `IOLoginData::loadPlayer` creates the item from `itemtype`, then calls `item->unserializeTVPFormat(propStream)`, which assumes the ID has already been read. Everything is read 2 bytes early: attributes are dropped, and a container's child count is read from the wrong bytes. The return value is ignored, so nothing is logged. The next save writes the damaged state back (backpack `C4070000000000000000`, i.e. 0 children), so **the loss is permanent**. Depot loading reads the ID itself, so it doesn't have this bug.

### 3. Control: skipping the ID fixes it

Same scenario, with only this one-line change in the inventory loader:

```cpp
propStream.skip(2); // blob starts with the item id written by serializeTVPFormat
item->unserializeTVPFormat(propStream);
```

Backpack contents, charges and description all survive, and the re-saved blob is byte-identical to the original.

![control fix](https://raw.githubusercontent.com/marcingoralski/TVPV8/2930297570f4ea169247ca4ca452295fc16df36d/evidence/fig3_control_fix.png)

### Found by reading the code, not reproduced here
- `Condition::serialize` / `unserialize` aren't overridden by any subclass, so subclass state is lost on relog: `ConditionDamage` damage list, `ConditionSpeed` speed delta, and the outfit, light, regeneration, soul and attributes conditions.
- `ADD COLUMN IF NOT EXISTS` and `TEXT ... DEFAULT ''` fail on MySQL; they only work on MariaDB.
- Nothing moves existing `.tvpp` data into the database, and old `player_items` rows use a different `pid` meaning, so upgrading a live server loses player data.
- `savePlayer` is now synchronous, roughly 15 queries inside a transaction on the dispatcher thread, so a server save stalls the game loop.
- `database.cpp` now logs failed queries in full, including escaped depot blobs. The 256-character cap should come back.
